# 手机拍屏幕行为检测预警系统技术调研（YOLO + VLM 两段式）

> 范围：办公室墙装摄像枪监控多台台式机，准实时检测"有人拿手机对着电脑屏幕拍照"行为并预警。调研 YOLO 对此类行为检测的能力边界、是否需要自训、LLM/VLM 的正确用法与延迟预算、硬件性能核算、开源替代商业方案（Zecurion）对比。

## 1. 总体结论

**技术可行，推荐"两段式"架构：YOLO 自训小模型做高频触发（每帧跑，毫秒级）+ VLM（Qwen2.5-VL 级别）做低频语义复核与取证（只对可疑片段跑，秒~分钟级）。**

核心判断：

1. **开箱即用的 YOLO（COCO 80 类）能做一半、做不了另一半。** COCO 有 `cell phone` 和 `laptop`/`tv`（显示器部分场景可召回）两个类，可以检出"画面里有手机""画面里有屏幕"；但"手机正对某块屏幕拍摄"是**两物体之间的空间关系 + 人的手臂姿态**，任何预训练检测器都不输出这种结论。这是行为/事件级问题，单帧检测器天生不回答"在干什么"。
2. **必须自己微调 YOLO，但工作量远小于直觉。** 业界已有成熟先例：FPI-Det 论文（2025，arXiv 2509.09111）在监控视角数据集上实测 YOLOv8-x 检手机 AP@50 = 92.4%（人脸反而只有 56.5%，手机是易检类）；多起"CCTV 手机使用检测"开源项目（两阶段：YOLO 定位人体 → 分类器判定 无手机/手持手机/举机）已验证该流水线在办公室监控下 MAP 92%+。自训重点不是"检手机"（简单），而是**场景适配**（俯视角度、远小目标、遮挡、桌面杂物的手机壳误报）。
3. **"对着屏幕"的判定建议用"检测 + 规则引擎"为主、"小分类器"为辅**，而不是指望检测器直接学出动作类。把"手举手机"作为一个**特殊检测类别**（如 `hand-phone`，框住手+手机整体）微调进去，再叠加几何规则：`hand-phone` 框中心落在显示器框附近上方/正前 + 持续 ≥N 秒 + 手臂朝向（姿态关键点可选）→ 触发候选事件。规则引擎可解释、可调参、误报可控。
4. **LLM/VLM 不能也不该逐帧跑**——你的直觉正确。VLM 的正确角色是**复核器 + 取证器**：收到 YOLO+规则的触发后，把该人 ROI 的连续 4~8 帧裁切图喂给 VLM，问一个封闭式问题（"此人是否正用手机拍摄面前的显示器？只回答 是/否 + 一句话理由"）。7B 级 VLM 单 clip 推理 10~60s（见 §5 延迟预算），对"预警"场景完全够用——触发本身是秒级，VLM 确认后推送带截图证据的告警。
5. **商业验证**：俄罗斯 Zecurion 的 DLP "Screen Photo Detector" 就是干这件事的商用产品（双神经网络、宣称 0.06s 检出、通过摄像头识别任意颜色/型号的手机、与 DLP 联动锁屏）。说明该问题有成熟解法但商业方案绑 DLP 生态、贵；自研两段式方案能力等价、成本可控。

## 2. 问题拆解：到底要检测什么

把"拿手机拍屏幕"拆成可检测的原子信号：

| 信号 | 性质 | 谁负责 | 单帧可判？ |
|---|---|---|---|
| 画面中有人（及归属哪台工位） | 目标检测 | 预训练 YOLO person 类即可 | ✅ |
| 画面中有手机/手持手机 | 目标检测 | 预训练 COCO cell phone 召回 + 自训提精度 | ✅（但"手持"与"放桌上"需自训区分） |
| 画面中有目标显示器及对应工位 | 目标检测 | 自训 `monitor` 类（俯视角度 COCO tv 召回差） | ✅ |
| 手机被举在手中（非持握通话/非放桌上） | **行为细粒度** | 自训检测类 `hand-phone` 或 ROI 分类器 | ✅（近似） |
| 手机镜头朝向屏幕（空间关系） | **关系推理** | 几何规则（bbox 相对位置 + 朝向）或 VLM | 规则近似 / VLM 精判 |
| 持续拍摄意图（排除路过、看手机） | **时序** | 跟踪 + 持续时间门控（≥3~5s，经验值需标定） | ❌ 需多帧 |

结论：**前 4 项是检测器任务（微调可达 90%+ 召回），第 5 项用规则覆盖 80% 场景、VLM 兜底，第 6 项是时间维度过滤——这三项组合即"行为分析"，没有任何单一模型一步到位，业界（含商用）也是这么拆的。**

## 3. YOLO 能力边界与自训必要性（详细调研）

### 3.1 预训练 YOLO 能做什么 / 不能做什么

- **能**：COCO 80 类中 `0: person`、`67: cell phone`、`68: laptop`、`72: tv`、`74: keyboard`、`76: mouse`。墙装俯拍场景下 person 稳定；cell phone 在**人近、手机大**时召回尚可，但墙装摄像枪典型 3~5m 俯拍，手机在 1080p 帧里常 <50px，COCO 手机检测的 AP 会显著下降（COCO 基准的手机本身是 COCO 80 类里 AP 倒数第几的小目标）。
- **不能**：
  - "手持 vs 放置"：COCO 不区分，桌上手机、口袋手机全部报 `cell phone` → 直接误报源头；
  - "手机对屏幕"：检测器无关系输出；
  - 显示器识别：办公显示器俯视角度、黑屏/亮屏、带支架，COCO `tv`/`laptop` 都不对口；
  - 动作语义："拍照片"这个行为词不在任何检测头里。
- **姿态估计（YOLO-pose）作为补充手段**：可给人体 17 关键点，"手抬到脸前/屏幕前"能用肘-腕-肩角度规则近似判断"举着东西"，但**无法判断手里拿的是什么**，且远处人关键点置信度骤降。定位为可选增强，不为主力。
- **YOLO 的"行为/动作"能力现状**：Ultralytics 官方任务矩阵只有检测/分割/分类/姿态/OBB/跟踪/深度估计，**没有动作识别任务**（那是视频模型领域：TimeSformer/VideoMAE/SlowFast 或 VLM 的事）。社区做法是把"行为"转成"可检测物体组合 + 规则"（如打架检测=多人+重叠+姿态异常）或"特殊类别检测"（如"手举手机"作为一个类）。

### 3.2 是否需要自己训练：是，且必要

**必须自训**，理由与工作量：

| 自训目标 | 为什么 | 难度 |
|---|---|---|
| `monitor`（工位显示器） | 俯视/远距/黑屏亮屏多变，COCO 无对应类；这是"对着哪块屏"的锚点 | 低（形态单一） |
| `hand-phone`（手举手机整体） | 区分手持/放置/通话，是触发条件的核心 | 中（需多姿势样本） |
| `cell phone`（保留，提小目标召回） | 补充兜底：手遮挡镜头时只露手机本体 | 中（小目标） |
| `person`（可不训，或轻量微调提远距召回） | 预训练已够用 | 低 |

**数据量经验值**（检测类微调，需按实测标定）：
- 每类 **500~2000 张**、总量 3~6k 张，是 2 类~4 类小目标微调的常用下限；
- 正负样本均衡很重要：大量"放桌上的手机""手持手机看内容（非拍摄）"负样本，直接决定误报率；
- **数据从哪来**：① 用现有摄像枪实拍 2~3 天（让不同同事配合摆拍各种姿势：举手机拍屏、看手机、接电话、手机放桌上、路过），最贴场景；② 网络素材（手机/办公桌面图像）补多样性；③ 无真实数据时可用合成（人+手机贴图）冷启动但泛化差，不推荐作为主力。
- **标注**：LabelImg / Roboflow / CVAT 均可，3~6k 张 2~4 类约 2~4 人天。
- **训练成本**：YOLO11n/s 级 4 类 3~6k 图，单张 2080 Ti 上 100 epoch 大约 **数小时级**（n/s 档）；x 档一晚上。这是整个项目里最便宜的部分。

**精度预期参考**：FPI-Det（监控视角，2025）YOLOv8-x 手机 AP@50 92.4%；CCTV 手机使用检测开源项目两阶段 MAP 92.6%。我们场景手机更小更俯，`hand-phone` 自训 AP@50 合理预期 85~93%（经验估计，需 PoC 标定），端到端"触发准确率"再由规则+VLM 两关提升。

### 3.3 备选：检测 + 独立小分类器（两阶段法）

业界另一主流拆法（CCTV Phone Usage Detection 等项目采用）：
1. YOLO 检出 person（预训练即可）；
2. 裁人 ROI，过小模型（MobileNet/EfficientNet 即可，<10ms）分类：`无手机 / 手持手机看内容 / 举机通话 / 举机对屏幕`。

- 优点：把"行为"收敛到 4 类图像分类，比让检测器硬学 `hand-phone` 空间关系更直接；分类器对"举机对屏幕"这种构图特征学起来快；
- 缺点：多一次推理、多一条训练流水线；人 ROI 在俯拍下可能截不全；
- **建议**：PoC 时两条路都试（A：检测4类+规则；B：person检测+ROI四分类），用同一套标注数据对比，谁准用谁。标注格式一次产出可同时喂两种任务。

### 3.4 许可证风险与开源替代（重要）

沿用 2026-08 许可证核查结论（`research/tech-research-wiki/references/license-verified-2026-08.md`）：

| 方案 | 许可证 | 商用风险 | 备注 |
|---|---|---|---|
| Ultralytics YOLO11/v8/v26 | **AGPL-3.0** | 中 | 内部部署不对外分发，AGPL 传染性风险低；若公司政策禁 AGPL，需购商业授权或换 Apache 系 |
| PaddleDetection + RT-DETR / PicoDet | Apache-2.0 | 低 | 性能同级、部署略繁琐（Paddle 生态） |
| YOLOX（原 DarkNet） | Apache-2.0 | 低 | 单阶段同级替代 |
| Qwen2.5-VL（VLM 复核） | Apache-2.0（代码+权重） | 低 | 3B/7B/72B 开源，可私有化 |
| InsightFace（如需人脸识别定责到人） | 预训练包**仅非商用** | 高 | 如需告警定位到员工，需向 insightface.ai 申请商用授权，或用其他开源人脸（如 insightface 之外的 ArcFace 复现）替代 |

**建议**：内部监控预警系统属封闭部署，Ultralytics AGPL 风险可接受（代码不分发、不对外提供网络服务）；若法务有顾虑，主线切 PaddleDetection RT-DETR（Apache-2.0），架构不变。

## 4. VLM/LLM 的角色设计与调用预算

### 4.1 为什么不能逐帧（算力账）

- 1080p@25fps 一路视频 = 25 帧/秒。7B 级 VLM（Qwen2.5-VL-7B）单图推理（低分辨率 token 上限下）约 1~5s/次（FP16，2080Ti 量级 GPU，经验值），逐帧跑 = 需要 5~125 倍算力，**物理上不可行**，且 VLM 输出 token 慢，天然不适合高频感知。
- 即使 VLM 只吃 1fps 抽样：25x 浪费，且"拍照"动作往往只持续 3~10s，1fps 抽样有漏检窗口。
- 正确分工：**高频感知（YOLO，全帧或 5~10fps 采样）→ 低频理解（VLM，仅触发 clip）**。这与商用 Zecurion 的"双网络"（快网络触发 + 精网络确认）是同一思想。

### 4.2 VLM 复核器设计

触发后，VLM 收到的是一个**结构化的待判问题**而不是裸视频流：

```
输入: 触发者 person-ROI 的连续 4~8 帧（每帧裁到 person+周边，缩放至 ≤640px 高）
      + 附带的检测器上下文（可选 prompt 注入："检测器报告：
        该人右手持手机，位置在显示器正上方 30cm 处，已持续 6 秒"）
Prompt（封闭式，强制短输出，压低生成 token）:
  "这些连续帧来自办公室监控。判断：该人员是否正用手机拍摄其面前的电脑显示器
   屏幕？注意区分：看手机内容、打电话、手机放在桌上都不算。
   只输出 JSON：{"shooting": true/false, "confidence": 0-1, "reason": 一句话}
输出预算: ≤60 token
```

- 用 **Qwen2.5-VL-7B（或 3B 更省）**，视频输入走其原生 `{"type":"video"}` 多帧接口（动态 FPS 采样 + MRoPE 时间编码，官方支持多帧/长视频）；
- 帧数 4~8 帧、`min_pixels/max_pixels` 压低（官方建议 256~1280 个 token 块区间内取低段）控制单 clip 到 **10~60s**（见 §5）；
- 输出结构化 JSON 直接进告警系统，`reason` 字段进审计日志（满足"预警要有依据"）；
- **VLM 的额外价值——取证与报告**：告警时自动生成"时间 + 哪个工位 + 哪块屏 + 截图 4 帧拼图 + VLM 一句话理由"的证据包，这是纯检测+规则给不了的，也是这个系统对管理侧最有力的输出。
- 置信度门控：VLM `confidence < 0.6`（经验值）时告警降级为"待人工确认"，不直接升级通报，压误报。

### 4.3 与"每工位摄像头"方案的关系

Zecurion 路线是**每台电脑配摄像头（1m 内近景）+ 双网络**，近景下手机占比大、判定容易、0.06s 级响应，还能联动锁屏。墙装摄像枪是**远景单点**，手机是远小目标，天然更难，所以我们的架构里规则+VLM 更重。若预算允许，最稳的混合方案：**墙装枪做全局行为筛查 + 重点工位（涉密/研发核心屏）加装桌面小摄像头做 Zecurion 式高精度确认**。本次调研以墙装枪为基准。

## 5. 性能与延迟预算（基于本机硬件）

硬件基线（见 memory：内网 LLM 硬件定案 2026-10）：双 2080 Ti 跑 llama.cpp Qwen3.8-27B-MTP-Q4 实测 52 t/s；L20 48GB 做 FP8+vLLM 主力；P4(sm_61) 仅适合小模型/embedding。

| 组件 | 模型 | 输入 | 部署 | 延迟/吞吐（经验值，需 PoC 实测） | 硬件落点 |
|---|---|---|---|---|---|
| 流处理 | 解码+抽帧 | 1 路 1080p25 | CPU/NVDEC | 25fps 轻松 | 任意 |
| 快检测 | YOLO11s（自训 4 类，640×640） | 全帧或 10fps 采样 | TensorRT FP16 | 单卡 200~500 fps，**1 路占用 <5%** | 2080 Ti × 1 |
| 跟踪 | ByteTrack/BoT-SORT（YOLO 内置） | 同上 | 同上 | <5ms/帧/目标 | 同上 |
| 规则引擎 | Python 状态机 | 检测+跟踪结果 | CPU | <1ms | 任意 |
| 慢复核 | Qwen2.5-VL-7B（或 3B） | 4~8 帧 ≤640px + 短 prompt | vLLM/SGLang FP16；2080Ti 上可用 AWQ/GPTQ-INT4 量化 | 单 clip 10~60s（输出强制 ≤60 token，瓶颈在 ViT 前向） | L20 优先；2080Ti×2 亦可（INT4 约 4~5GB 权重，sm_75 无 FP8，量化后单卡可容） |
| 告警推送 | 截图拼图 + JSON | — | CPU | 秒级 | 任意 |

**端到端时延**：行为发生 → YOLO 检出（≤1s）→ 持续门控 3~5s → VLM 复核 10~60s → **告警发出：行为开始后约 15~70s**。对"检测+预警"场景达标（不是实时阻断，是准实时取证预警）；若要求 <3s 阻断级，只有桌面近景摄像头方案能达（见 §4.3），墙装枪+VLM 做不到，需明确需求边界。

**并发核算**：
- 检测端：单张 2080 Ti 扛 **8~16 路 1080p** 检测流无压力（10fps 采样下每路 ~50ms GPU 时间）；
- VLM 端：告警是低频事件（正常办公室预期每天个位数到几十次），单 clip 占 L20 半分钟，**一天几百次告警也不会排队**；并发 3~5 个 clip 排队也只在极端的"集体拍屏"场景出现，可接受；
- 结论：**现有 L20 + 2080Ti 存量硬件完全够用，无需新增卡**。

## 6. 系统架构

```
 墙装摄像枪(1080p25)
        │ RTSP
        ▼
 ┌──────────────┐   10fps 采样帧
 │ 流处理/解码   │──────────────┐
 └──────────────┘              ▼
                        ┌────────────────────────────┐
                        │ YOLO11s 自训 (TensorRT)    │  person / monitor /
                        │ + 跟踪 (ByteTrack)         │  cell phone / hand-phone
                        └──────────────┬─────────────┘
                                       │ 每帧 4 类 bbox + track_id
                                       ▼
                        ┌────────────────────────────┐
                        │ 规则引擎(每 track 状态机)    │
                        │ 1. 同 track 有 person       │
                        │ 2. 有 hand-phone 或 phone   │
                        │ 3. 手机中心 ∈ 某 monitor     │
                        │    框上方/正前 扩展区        │
                        │ 4. 持续 ≥ 4s (经验值)       │
                        │ 5. (可选) 姿态: 腕高于肩      │
                        └──────────────┬─────────────┘
                                       │ 触发: 裁该 track 前后各 ~4s 帧 → clip
                                       ▼
                        ┌────────────────────────────┐
                        │ Qwen2.5-VL-7B (vLLM)       │
                        │ 封闭式判定 + JSON 输出       │
                        └──────────────┬─────────────┘
                              ┌────────┴────────┐
                        conf≥0.6│                  │conf<0.6
                               ▼                  ▼
                        ┌─────────────┐    ┌──────────────┐
                        │ 告警(即时推送)│    │ 待人工确认队列 │
                        │ 截图拼图+证据 │    └──────────────┘
                        │ +工位+时间    │
                        │ +VLM理由     │
                        └─────────────┘
                        全程录像回存(按事件±30s 切片归档)
```

**工位映射**：离线标定一次——把每台显示器在画面中的框 + 工位编号配进配置（自训 `monitor` 类检出后按位置匹配），告警即可定位到"3 号工位"。

**关键参数（均经验值，PoC 标定）**：
- 检测置信度阈值 0.4（手手机类可降到 0.35 提召回，靠后续两级压误报）；
- 触发持续时长 4s（<3s 多为路过/短暂查看；>6s 会拖慢告警）；
- VLM 采样帧 6 帧、clip 长度触发前 2s~触发后 4s；
- VLM 置信度门控 0.6。

## 7. 风险与缓解

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| 远小目标手机漏检（3m+ 俯拍） | 高 | 漏报 | 摄像枪位置尽量压低俯角；imgsz 640→1280 对疑似区域做二次放大检测（SAHI 式切片，只对含 person 帧启用，成本可控）；重点屏加桌面近景枪 |
| 手机放桌上/看手机被误触发 | 高 | 误报（系统信誉杀手） | 负样本重点标注；持续时长门控；VLM 复核强制区分"看内容 vs 拍摄" |
| 隔着手机壳/不同机型/横竖屏 | 中 | 漏检 | 训练数据覆盖多壳多机型；`hand-phone` 类以"手+手机"整体为框，降低对手机本体的依赖 |
| VLM 慢/不可用 | 低 | 告警延迟 | VLM 降级策略：超时 90s 按"检测器高置信(>0.85)直接告警、中置信入人工队列" |
| 隐私合规（监控员工行为） | 中 | 法律/管理 | 仅在工作区域工作时间开启、显著告知、数据仅存 7~30 天、VLM 本地化不出内网、告警走 IT 安全流程而非直接通报个人 |
| Ultralytics AGPL | 低 | 法务 | 内部部署不触发分发条款；如需规避切 PaddleDetection RT-DETR（Apache-2.0） |
| 夜间/低照度 | 中 | 漏检 | 摄像头补光/红外（红外下手机检测需补对应数据）；非工作时间降灵敏度或仅录像 |
