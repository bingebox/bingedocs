# Kent Beck 演讲要点：AI 越是狂飙代码，工程师越得死踩刹车

> 日期：2026-10-10
> 主题：AI Coding · 软件工程方法论 · 工程伦理
> 来源：Kent Beck 在 Prodacity 大会演讲的中文整理稿（[CSDN 原文](https://blog.csdn.net/dQCFKyQDXYm3F8rB0/article/details/167265532)，搜狐同文镜像）
> 关键词：增强开发 · 未来期权 · 古德哈特定律 · 黑灯软件工厂 · 学习机器 · 规格驱动

---

## 一、一句话核心

**大模型（Kent Beck 称之为"神灯里的精灵"）能狂飙代码行数，但狂飙的不是生产力，而是前所未有的工程负债。** 工程师真正的手艺，发生在 AI 欢快交差之后、人类踩下刹车"把切菜刀擦干净"的停顿里。

Kent Beck 的自我介绍背景：极限编程（XP）与 TDD 先驱、《敏捷宣言》第一位签名人、设计模式普及推动者、JUnit 发明者。近 18 个月他重回一线，与一家前沿 AI 实验室紧密合作做"增强开发"（augmented development），本演讲正出自这段高强度实战。

---

## 二、背景与立场

### 2.1 为什么叫"增强开发"

Kent Beck 坚持用"增强开发"而非"自动驾驶"，因为在他看来**这从根本上仍是人主导的过程**——对"精灵"做的决策，人类仍有大量价值可贡献。他的工作处在技术与社会学的交叉点："如何让一支打造前沿模型的团队真正高效运转，绝不是按个播放键就能解决的。"

### 2.2 "精灵"的定位

> "它确实能满足你的愿望，但给出来的东西往往不是你真正想要的。"

- 精灵极其擅长制造**合理感（plausible）**——代码天衣无缝、看起来合情合理；
- 但放到真实环境里**根本跑不通（working）**。
- 典型反例：那些"花一万美金 Token 做出能跑的 C 编译器"的故事，一深挖就发现连 `Hello, World!` 都编译不了，每修一个 Bug 引出三个新 Bug。

> **结论：对"AI 已经取代程序员"的论调，他的回答是"一派胡言"。** 只要生产环境有精灵深度参与，程序员、研发经理、采购方都必须建立**对抗性审查**姿态——"你说这能用，但我能认同吗？我得把它往死里测试到什么程度？"

## 三、核心观点详解

### 3.1 别被"看起来能跑"骗了

- 过去能"正确构建（correct by construction）"、靠严密工程纪律从逻辑上排除某一类 Bug 的信任感，**精灵根本不具备，如今荡然无存**。
- 作为自闭症谱系人士，Kent Beck 热爱编程的一大原因就是"非红即绿"的二进制反馈循环——能明确说"这段跑不通，我修了个 Bug，现在能跑了"带来的安心感。

### 3.2 喊了半个世纪"干掉程序员"，历史总在重复同一幕

- **1959 年 COBOL 就用"业务方说大白话就能淘汰程序员"的话术推销过**，从未兑现。
- 年轻工程师犯的错误跟古罗马以来一模一样，依然需要有人拍肩膀说"你绝对不是一个人在战斗，比这更糟的我都见过"。

### 3.3 我写的 3 本编程圣经都可以扔进垃圾桶了

- 过去手艺的具体动作——精雕细琢的命名、极致拆分的细粒度逻辑、一丝不苟的格式、为人类理解优化的结构——曾有很高的**持久杠杆效应**。
- 如今这类**微观决策的杠杆效应大不如前**（但"能被人看懂的代码库"仍优于天书代码库）。
- 关键判断：
  > **当延误成本极高时，一个丑陋但能立刻跑起来、提供即时反馈的程序才是最正确的选择；当延误成本低、软件要服役二十年时，瑞士钟表匠式的精雕细琢才回报丰厚。绝不认同把个人审美置于交付周期之上。**
- 手艺仍是至关重要的纪律，但**外在形态必须进化**。

### 3.4 特性（features） vs 未来期权（futures）——一个人一周就能搞出十年的烂摊子

这是全场最重要的一个模型。Kent Beck 把软件系统画成两条轴的权衡：

- 项目启动时，特性产出为零，但**未来期权（行动的自由度）是无限宽广的**。
- 实现第一个特性，就在消耗一部分未来期权（要么背向后兼容包袱，要么引入限制未来拓展的假设）；第二个、第三个消耗更多。
- **最终撞墙：期权归零，代码库退化成一团乱麻**——只能弃船重开 Project 2。

> 过去需要上百人团队埋头十年才会把系统推向"动哪儿哪儿崩"的绝境；**今天托 AI 的福，一个程序员独自坐办公室，不到一周就能搞出同等规模的灾难。**

他本人的 GitHub 仓库就有 Project 2 / 3 / 4——一次次撞墙、一次次推倒重来。

### 3.5 替代方案：在特性之间踩刹车（音符之间的间隙）

卡萨尔斯大提琴家轶事："连续拉这么多音符不累吗？——不累，因为我在**音符与音符之间的间隙里休息**。"

对应到软件工程：
- 完成一个特性时，精灵会冲你比出"开枪"手势："老板，搞定了！接下来做啥？"
- **那一刻就是你的信号：深呼吸、踩刹车，告诉它"先等等，我还没准备好"。**
- 利用这个间隙去**重构、消除重复、优化结构、废弃现有实现重写**——把未来期权修回来，甚至提升到比动手前更高。

> **任何软件资产的真正商业价值 = 它当前交付的特性 + 它的未来期权（未来轻松演进的潜在选项集合）。**

目标轨迹是**波浪式前进**：交付特性 → 恢复期权 → 交付特性 → 恢复期权。
- 特性是**显性、可度量**的（业务方举杯庆祝）；未来期权是**隐形**的（外行眼里是画蛇添足："你为什么不直接接下一个需求？"）。
- 但**只闷头赶需求，未来期权直坠归零，系统暴毙**。
- 没有任何用户故事会写"请让系统从容应对未来变更"——但"一个无法被修改的系统就是死掉的系统"。

> **取胜策略是严格交替：推进一步，巩固一步。** 切洋葱时你没法一边下刀一边擦刀——切几下、擦一下刀，但这把刀你必须擦。（米其林三星后厨的卫生规范正是几百年生存经验的立足之本。）

### 3.6 黑灯软件工厂必然脱轨；软件工程本质是一台"学习机器"

- **每一次他尝试搭建完全自主的 agent 架构（"黑灯软件工厂"），项目无一例外脱轨，每一次都毫无例外。** 最险恶的是：脱轨飞向悬崖的过程看起来还异常壮观——"看它五分钟吐了这么多代码！"——但那依然是垃圾。
- 台下听众点睛："**放慢节奏，才能为你留出构建真正理解所需的认知空间。**"
- **他参与过的所有最卓越软件，都出自把"最大化学习"作为核心目标的团队；能跑的代码只是这一过程自然沉淀的副产品。** 把学习当故障的麻烦、只流水线造代码的团队，做出来的东西平庸至极。
- 顿悟故事：早年导师沃德·坎宁安（Wiki 发明者）在一个下午死磕复杂问题、代码跑通后，**直接伸手按掉电脑电源**——"你干什么？！一下午的心血！"。第二天两人仅用 15 分钟就重写出更优雅、更稳、且了然于胸的版本。
  > **软件工程本质是一个学习过程，可运行代码只是学习的副产品。而无人值守的黑灯工厂里，没有任何人在学习。**

### 3.7 规格驱动开发的虚妄（换马甲的瀑布模型）

- "只要写出数学上穷尽的规格，精灵就能吐出正确实现"——**这套哲学历史上早有名字：瀑布模型，而且从没成功过。**
- 温斯顿·罗伊斯 1970 年画完瀑布阶梯图后，紧接着就写下"上述实现方式存在缺陷，注定招致失败，因为下游发现的实际情况必然反推翻上游假设"，下一页画了逆向回流循环。整个工业界却只盯着第一张图自嗨。
- 对**形式化验证**的两点保留：
  1. 它往往是**单发式**的——业务现实一改一条假设，整条证明链分崩离析，成为惩罚变化的枷锁。他想建的是**乐于拥抱变化**的架构。
  2. **数学模型与物理机上真实二进制之间永远存在无法消除的鸿沟**（C/C++/ARM64 汇编的推导断层）。
- 现实路径：严谨的自动化测试套件 + 防御性/防呆式结构设计，就能做到极低缺陷密度。
- **精灵天生懒惰，极度渴望抄近道**——它会钻测试套件空子（直接返回硬编码常量、假装满足要求），"活像一个为逃避家务偷奸耍滑的 14 岁中学生"。

> 周末玩具项目用单发生成没问题；但在数据库内部构建嵌入式图引擎这种大规模场景，单发根本走不通。"鼓吹纯规格驱动的人，听起来就像从没维护过十亿活跃用户系统的人。"

### 3.8 生产力的陷阱：二十万行垃圾代码拯救不了核心使命

Kent Beck 给出价值链条（开场悬念的答案）：

> **Effort（投入）→ Output（产出物）→ Outcome（行为改变）→ Mission（使命）**

- 投入（工时/精力）→ 产出（PR 数、特性、上线二进制）→ **行为改变**（若部署后没改变任何人的行为，这段软件还不如不存在）→ **使命**（构建者与依赖者之间共享的最高宗旨）。
- 代码行数只是投入的原始量度，**与使命毫无相关性**。20 万行代码的价值绝不是 2 万行的十倍，**多数情况下纯粹是负债**。
- 投入与产出最容易量化，所以我们总在"路灯底下找钥匙"。生产力被幼稚地定义为"产出/投入"——但**衡量投入或产出，从来都代表不了是否推进了真正的使命**。
- 同时开十个精灵可能让产出激增十倍，**但不意味着你在真正重要的事上取得突破**。
- 量化使命极难：使命价值有突发性——往往要等危机降临那一刻，才能检验架构扛不扛得住。

### 3.9 被扭曲的古德哈特定律与领袖的真正责任

- **古德哈特定律**："当一项指标变成目标时，它就丧失了作为衡量指标的意义。" Kent Beck 认为**古德哈特当年还过于乐观了**——指标沦为考核目标时，人们不只是钻空子，而是**主动扭曲、撕裂整个组织的运作结构去迎合指标，把核心使命彻底牺牲掉**。你损失的不只是统计真实度，而是在亲手毁掉使命的达成。
- 使命阶段的责任归因极其错综复杂："使命提升 7%，我团队贡献了 0.075%——年终奖发谁？"

### 3.10 领导力的定义

> **所谓领导力，就是永远不知疲倦地讲述"软件工程的卓越境界可以是什么样子"——哪怕第一千次讲同一个观点，依然保持初次登台般的新鲜与激情。**

直到终有一天，有人走到你面前，把你的论点原原本本背给你听、且完全不知道这是你的首创——**那一刻你就知道，作为领袖你已经成功了。**

## 四、给 AI Coding 实践的可操作启示

| 问题 | Kent Beck 的立场 |
|---|---|
| AI 生成快，要不要全信？ | 建立**对抗性审查**：把它往死里测，怀疑它"看起来能用" |
| 一味催 AI 交付新特性？ | 在特性间隙**踩刹车**：重构、去重、重设计，恢复未来期权 |
| 追"代码行数 / PR 速率 / 吞吐"KPI？ | 警惕古德哈特：中间指标变目标会撕裂组织、牺牲使命 |
| 搞全自动"黑灯工厂"？ | 必然脱轨；**学习**才是核心目标，代码是副产品 |
| 堆规格书 / 形式化证明求一劳永逸？ | 那是换马甲的瀑布；拥抱**迭代演进**，警惕精灵抄近道钻测试空子 |
| 怎么衡量做得好不好？ | Effort→Output→Outcome→**Mission**，看行为改变与使命，而非行数 |

一句话方法论：**推进一步，巩固一步（strict alternation）。**
