# Qwen3.8-27B 各版本变体调研：功能差异与选型

> 范围：Qwen3.8-27B 官方发布形态、社区量化/MTP/免审查变体的功能差异、精度损耗与按硬件的选型建议。数据来源：Hugging Face 官方与 unsloth 模型卡、DataLearner 量化指南（2026-08-19）、lcz.me 双 27B 部署实测（2026-08-20）、本机双 2080 Ti 实测（2026-09）。

## 一、核心结论（先读这段）

**Qwen3.8-27B 的所有"版本"都是同一个模型**（27.78B dense，Gated DeltaNet+Gated Attention 混合注意力，64 层，原生视觉，262K 原生上下文可扩展 1M，Apache 2.0，内置 MTP 训练头）。变体之间的差异只有三类，**没有任何变体增加功能**：

1. **量化精度**（BF16 → FP8 → Q8/Q6/Q5/Q4/Q3 → NVFP4/IQ2）：决定显存占用和极小的精度损耗；
2. **是否带 MTP 投机解码头**：决定能否一次前向验证出 2 个 token（速度近翻倍，输出质量不变）；
3. **是否改过行为**（免审查/abliterated 微调）：改变拒答行为，不改能力上限。

功能（视觉/视频输入、思考模式开关、reasoning_effort 档位、工具调用、长上下文）**在所有变体中一致**，差异只体现在部署框架支持、速度和精度上。

## 二、官方发布形态

| 版本 | 权重体积 | 框架 | 精度 | 定位 |
|---|---|---|---|---|
| **Qwen/Qwen3.8-27B** (BF16) | ~54.7GB | Transformers/vLLM/SGLang | 原始 | 参考基线，单消费卡放不进 |
| **Qwen/Qwen3.8-27B-FP8** | ~28GB | vLLM/SGLang/Transformers | 细粒度 FP8（block 128），官方称"指标与原版几乎一致" | 生产部署主力，L20/H100/4090 级别单卡可用 |
| **unsloth/Qwen3.8-27B-NVFP4** | ~15GB（NVFP4 混合） | SGLang/vLLM（需 sm_120 Blackwell 或对应 kernel） | 4-bit NVFP4（MLP 主干 NVFP4 + attention F8→BF16） | 新一代 4-bit 生产档，Blackwell 专属优势 |
| **Qwen Cloud 托管版**（coming soon） | — | 官方 API | — | 默认 1M 上下文、官方内置工具；本地部署无需关注 |

要点：
- **FP8 是官方的"生产量化"**，Turing（2080 Ti）无 FP8 Tensor Core 会退化为软件模拟（本机实测仅 5 t/s），Ada（L20）/Hopper/Blackwell 上原生加速。
- NVFP4 官方口径是 Unsloth/RadixArk 出品，RadixArk 版附 SGLang NEXTN 投机解码配方（`--speculative-algorithm NEXTN --speculative-num-steps 3`）。
- 三个官方/准官方形态都**自带 MTP 头**（NextN 张量），投机解码是模型内建能力，不是外挂。

## 三、社区量化版本（GGUF 生态，llama.cpp/Ollama/LM Studio）

以 unsloth/Qwen3.8-27B-GGUF（Dynamic v3.0 量化）为主力参考系：

| 量化 | 体积 | 显存档位 | 精度/能力损耗 | 说明 |
|---|---|---|---|---|
| Q8_0 | 29.0GB | 48GB+ | 接近无损 | 有富余就选它 |
| Q6_K | 22.9GB | 32GB+ | 高质量 | 严肃 Coding Agent 的下限档 |
| Q5_K_M | 19.8GB | 24GB+ | 质量/资源折中 | ⚠️ 部分卡上 Q5+MTP 组合有崩溃报告（见第七节坑） |
| **UD-Q4_K_XL** | 17.9GB | 24GB+ | 同 Q4 档质量最佳（Dynamic 按张量重要性分配 bit，MMLU 5-shot 接近 Q5_K_M） | 24GB 卡首选 |
| Q4_K_M | 17.1GB | 24GB+ | 通用 4-bit，高难任务/Q4 档下有可测的细微退化 | 最通用，兼容性最好 |
| UD-Q3_K_XL | 13.4GB | 16GB+ | 妥协档 | 16GB 卡可用，agent 场景非长期最佳 |
| UD-IQ2_XXS | 9.0GB | 极限 | 体验版 | 只适合"看看模型长什么样" |
| MTP 独立草稿文件 | 1.37GB | +1.4GB | — | unsloth 仓库 `MTP/mtp-Qwen3.8-27B-Q4_0.gguf`，给不带 MTP 头的主模型补投机解码用 |

**精度损耗量化参考**（AtomicChat 统一 held-out 测试，KL Divergence / Top-1 Agreement 对比 BF16）：Q4 档 PPL 已非常接近原模型，但 token 级行为与 BF16 有可测差异；高难任务和复杂 agent 场景 Q5/Q6 更稳。结论：日常/检索类任务 Q4 足够，严肃 Coding Agent 尽量 Q5+。

另有细分档位：
- **HauhauCS Q4_K_P**（5.25 BPW，高于 Q4_K_M 的 4.88）：同体积精度高一档，社区实测与 UD-Q4_K_XL 同速（68.4 vs 67.2 t/s @ RTX PRO 4500 32GB）。
- **vmarcelo/Qwen3.8-27B-MIX_GGUF**：针对 16GB 显存的混合量化定制（~14GB，接近 4-bit 质量）。
- **esatapedico NVFP4-MTP-GGUF 九档**（14.86~33.13GB）：NVFP4 主干 + 按 lm_head/embedding/MTP 头分档混合量化，**要求 sm_120（Blackwell）**。
- **mlx-community/Qwen3.8-27B-4bit**：Apple Silicon 专用，M4 Max 36GB 实测 ~23.5 t/s，M5 Max 优化 4bit+MTP 社区 50~60 t/s。

## 四、MTP 变体（速度变体，非功能变体）

Qwen3.8-27B **训练时就带了多步 MTP 头**（`blk.64.nextn.*` 张量），所以：

- 多数新发布的 GGUF（UD 系列、MTP-GGUF 仓库）**MTP 头已烤进主文件**，llama.cpp 加 `--spec-type draft-mtp --spec-draft-n-max 2` 即可启用；带 `noMTP` 后缀的是阉割版，提速功能不可用。
- 旧/精简主模型可外挂独立 MTP 草稿文件（~1.4GB）实现同样效果。
- HauhauCS 的 **FastMTP-32K sidecar**（0.9GB，宣称再快 ~35%）：社区实测**弃用**，收益不实。

MTP 收益与代价：
| 场景 | 无 MTP | 开 MTP | 备注 |
|---|---|---|---|
| RTX 5090 Q5 | ~66 t/s | ~121 t/s | 近乎翻倍 |
| RTX PRO 4500 Q4_K_M | 40-41 t/s | 57-68 t/s | 接受率 54-68%，agent 工具调用负载下偏低属正常 |
| 双 2080 Ti Q4_K_M（本机实测） | 27 t/s | 52 t/s | 一次前向出 2 token |

代价：MTP 头吃掉额外显存（~1-1.5GB + 草稿 KV），压缩可用上下文。**输出质量与不开 MTP 逐 token 一致**（验证机制保证）。

## 五、行为变体（免审查/微调）

| 变体 | 变化 | 能力 | 适用 |
|---|---|---|---|
| HauhauCS Aggressive（含 MTP GGUF） | 去拒答 profile，实测 0/465 refusals | 与底模持平（Q4_K_P 量化） | 内网离线、不需要安全护栏的场景 |
| abliterated 系列 | 去除拒答特征 | 同上 | 同上 |
| 社区 SFT/蒸馏微调（如 Qwopus 系列，基于 3.6） | 特定能力增强（token 效率 +16.6% 等） | 窄域增强，无标准基准全集验证 | 实验性，生产慎用 |

这类变体**只改行为不改架构**，量化档位、MTP 支持与对应底模一致。

## 六、按硬件的选型（功能精度速度综合）

| 硬件 | 推荐 | 理由 |
|---|---|---|
| 2080 Ti ×2（Turing，22GB） | llama.cpp + **Q4_K_M-MTP**（或 UD-Q4_K_XL-MTP） | FP8/NVFP4 无硬件支持；llama.cpp 层切分不吃卡间带宽；实测 52 t/s |
| L20 48GB（Ada，单卡） | **FP8 + vLLM/SGLang + MTP 投机解码** | Ada 原生 FP8；~28GB 权重留 ~18GB 给 KV，支持多路并发 + 32-64K 上下文，精度三者最高；单流速度开 MTP 后与 llama.cpp 同量级 |
| 4090/3090 24GB | llama.cpp + UD-Q4_K_XL + MTP（~17.9GB+1.4GB） | 24GB 甜点区；SGLang+AWQ 亦可（3090 实测 ~43 t/s） |
| 32GB（RTX PRO 4500/5090） | llama.cpp + Q4 档 + MTP，200K 上下文 | 社区压测零崩定案；Q5+MTP 在 sm_120 有崩溃报告 |
| 48GB+ 单卡且纯单用户 | Q6_K 或 Q8_0 + MTP | 追求精度上限 |
| 多人并发服务（任意 24GB+ 卡） | 优先 FP8/NVFP4 + vLLM/SGLang | llama.cpp 并发调度弱，单用户场景才占优 |
| Apple Silicon 32GB+ | MLX 4bit（+MTP） | 统一内存优势，decode 带宽受限下量化收益大 |

选型三原则（DataLearner 指南）：
1. **先定显存预算再反推量化**，模型文件大小 ≠ 运行显存（KV cache + runtime buffer + MTP 头 + 视觉组件另算）；
2. **报速度必须带条件**（量化/后端/上下文/是否 MTP/decode 还是 prefill），agent 场景 prefill 往往比 decode 更影响体验；
3. **同名量化可能差几百万字节**（带不带 MTP 头、带不带 vision），下载后 `llama-gguf <file> r | grep nextn` 验证 MTP 张量是否在场。

## 七、坑与注意事项

1. **Q5_K_M + MTP 在 Blackwell sm_120 有必崩报告**（decode kernel 超驱动看门狗，`launch timed out`）；Q4 档 + MTP 是已验证的安全组合。`illegal memory access` 则是显存不足，两种崩溃方向不同。
2. **MTP 吃显存**：开 MTP 后长上下文预算要相应下调；288K+ 档位偶发 Xid 8，200K 是 32GB 卡社区定案。
3. **3.8 默认思考模式且"过思考"是祖传毛病**：部署时 `reasoning_effort=medium/low` 压住，检索/OCR 归类类任务深度思考纯浪费延迟；`preserve_thinking` 用于多轮 agent 会话保留思考连续性。
4. **官方 jinja 模板会把空 thinking 块包进输出**，破坏多轮 agent 会话，llama.cpp 部署注意 `--reasoning-preserve` 或自定义模板。
5. **NVFP4 GGUF 需要较新 llama.cpp**（GGML type 40 + sm_120 CUDA kernel），老卡上 NVFP4 生态无意义。
6. FP8 模型在 Ampere（30 系）上 vLLM 可用 Marlin kernel 跑，但无 Ada/Hopper 的吞吐。
7. 免审查变体无完整安全评估，内网对公业务建议用官方版 + 应用层护栏。

## 八、对本公司环境的落地结论

| 环境 | 定案 |
|---|---|
| 双 2080 Ti 内网机 | llama.cpp + Qwen3.8-27B-MTP-Q4_K_M，52 t/s，作为轻量/备份推理节点；上下文压到 8-16K |
| L20 48GB 单卡 | Qwen3.8-27B-FP8 + vLLM（开 MTP 投机解码），主力服务节点，多路并发 + 32K 上下文；reasoning_effort 默认 low/medium |
| 截图检索系统接入 | 走 L20 主力节点的 OpenAI 兼容 API，任务为 OCR 结果归类/检索词生成/结构化抽取，无需深度思考档 |
