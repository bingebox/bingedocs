# 单卡 96G 跑 27B 大模型，我把推理速度提升了 3~4 倍

一台 RTX PRO 6000 Blackwell（96GB），
跑 Qwen3.8-27B 编程助手，262K 上下文。

不动权重、不做量化、不 OOM，
把稳态生成吞吐从 27 提到 80~105 tokens/s。

过程踩了不少坑，这篇文章记录完整路径。

## 一、环境一览

- GPU：RTX PRO 6000 Blackwell，96GB
- 模型：Qwen3.8-27B，BF16 权重约 54GB
- 框架：vLLM 0.27.1 + FlashInfer
- 上下文：262K（256K）
- 场景：AI 编程助手，实时对话 + 工具调用 + 截图输入

三条优化约束：

1. 不牺牲推理效果，不做权重量化；
2. 显存不能 OOM；
3. 一次只动一个变量，可独立回退。

## 二、起点：慢，但稳

基线数据（2~4 并发）：

- 生成吞吐：典型 ~46 tok/s
- 显存：94.3 / 97.9 GB
- 温度功耗：80°C / 300W 封顶
- 前缀缓存命中率：~43%

诊断结论：

显存几乎吃满，吞吐却远低于硬件能力。

不是硬件问题，是配置问题。

为什么显存这么紧？

27B 的 BF16 权重 54GB，是固定开销。

262K 上下文的 KV Cache 吃掉剩下的空间。

96GB 刚好够，几乎没有余量。

所以原则只有一条：别堆参数，逐个调。

## 三、两个大坑

### 坑一：JIT 编译失败

第一次优化启动直接崩，报错核心是：

```
fatal error:
cuda_runtime.h: No such file or directory
```

原因：

FlashInfer 需要现场 JIT 编译内核，
nvcc 编译器明明装着，
但 nohup 拉起的后台进程没继承 CUDA_HOME 和 PATH。

修复就两行，写在启动脚本里：

```
export CUDA_HOME=/usr/local/cuda-13.0
export PATH=$CUDA_HOME/bin:$PATH
```

### 坑二：堆参数，OOM

照着大模型给的"一键优化脚本"，
fp8 KV、autotune、提并发……一次全加上。

服务起来了，
但发一个 "hi" 就 OOM，显存只剩 4.5MB。

教训：

一把梭改动 = 事故预案。

生产调参一次只动一个变量，
每步观察至少一天，能独立回退。

## 四、走通的路径：两步

回退到稳定基线（27 tok/s）后，分两步优化。

**第一步：注意力后端切到 FlashInfer**

```
export VLLM_ATTENTION_BACKEND=FLASHINFER
```

同时移除原来的 VLLM_DISABLE_FLASHINFER=1。

保留 VLLM_USE_FLASHINFER_SAMPLER=0，
Blackwell 上采样器有已知问题，必须绕开。

注意：第一个请求会卡 2~5 分钟，
那是 JIT 编译，等就行，千万别重启。

结果：27 → 50~72 tok/s。

中间还出现过一个"假崩溃"窗口：
KV 打满 99.7%，生成跌到 0.9 tok/s。

实际是冷启动 + 长 prompt 预填充突发，
几分钟自己恢复到 70+。

结论：别拿单张快照下"性能崩溃"的判断。

**第二步：KV Cache 降 FP8**

```
--kv-cache-dtype fp8_e4m3
```

KV 读取带宽减半，容量翻倍。

权重保持 BF16，效果无损。

结果：80~105 tok/s。

对比基线，净改动只有上面两处
加 CUDA 环境修复，
每一行都有独立回退路径。

## 五、关键教训

1. 别迷信"一键优化脚本"。
大模型编造了十几个不存在的参数
（--performance-mode、--watermark、
--enable-flashinfer-autotune 等），
每个参数都要对照官方 help 核实。

2. 吞吐有两个口径。
80~105 tok/s 是整机合计（4~6 并发），
单请求折算约 14~26 tok/s，
两个口径别混着说。

3. 提示词头部别放时间戳、随机串，
否则前缀缓存命中率直接归零，
首 token 延迟会明显变差。

4. 评估看 P99，不看均值。
262K 长上下文请求就是长尾，
均值会把它们藏起来。

5. 启动后前 2~5 分钟是 JIT 编译，
首请求延迟尖峰是正常现象。

## 六、结果

- 基线：~27 tok/s
- + FlashInfer：50~72 tok/s
- + FP8 KV：80~105 tok/s，约 3~4 倍
- 显存：稳定 95.5GB
- 温度 / 功耗：79°C / 324W

（插图：Grafana 稳态面板，
Prefill 均值 3541 tok/s，Decode 均值 41.1 tok/s）

## 七、调优侧重点（给同样场景的人）

编程助手是实时交互场景，
要看的是单请求体验，不是整机合计数字。

1. 先看两个延迟指标：
TTFT（首 token 延迟）、TPOT（每 token 延迟），
看 P99，不看均值。

2. 并发不是越大越好。
实际工作点是"仍满足 TPOT P99 的最大并发"，
用压测并发扫表找，别拍脑袋。

3. KV 使用率是停止线，
逼近 80% 就停手。

4. 别追整机吞吐数字。
交互式服务里，
它只能用单请求延迟去换。

## 八、后续方向

- 试 VLLM_USE_FLA=ON
（线性注意力算子，独立变量单独验证）；
- 并发上探（FP8 KV 已释放容量）；
- FP8 权重（若未来效果约束放松，
54GB → 27GB，KV 余量翻倍）。

---

方法论一句话：

**显存预算先行 → 稳定基线锚定 →
单变量分阶段 → 每步独立回退 →
用 SLO/Goodput 锚定评估口径。**
