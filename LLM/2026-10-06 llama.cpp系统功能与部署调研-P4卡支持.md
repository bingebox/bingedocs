# llama.cpp 系统功能与部署调研（含 P4 卡支持分析）

## 一、核心结论（先读这段）

1. **llama.cpp 定位**：GGUF 量化模型的本地/边缘推理引擎，主打"无框架依赖、单二进制、OpenAI 兼容 API"。与 vLLM 互补：vLLM 吃满大显存卡（FP8/高吞吐/batch），llama.cpp 吃小显存和 CPU（量化/单机/低配卡）。
2. **P4 卡支持 = 可以，但不是开箱即用**。P4 是 Pascal sm_61，CUDA 12.x 仍完整支持；**CUDA 13.0 起已彻底移除 Pascal 编译支持**。必须**源码自编译**（`-DGGML_CUDA=ON -DCMAKE_CUDA_ARCHITECTURES=61`）或用指定 `CUDA_DOCKER_ARCH=61` 自构建 Docker 镜像，官方预编译二进制/镜像（默认只含 Turing+）在 P4 上会**静默回退 CPU**（报 `forward compatibility was attempted on non supported HW`，GPU 空转）。
3. **P4 能跑什么**：8GB 显存 + 32GB/s 带宽（无 Tensor Core）→ 适合 ≤8B Q4/Q5（全量 offload，约 5~10 t/s 生成），或 14B~27B 的"部分 offload + CPU 混合"（速度慢，仅适合低并发/非交互场景）。不适合当主力服务卡——**内网主力仍是 L20 + vLLM，P4 适合做小模型辅助节点**（embedding、分类、路由、小模型对话）。
4. **风险点**：P4 需 NVIDIA 专有（proprietary）驱动；CUDA 13 生态（cuBLAS/cuDNN 新版）不再出 Pascal 库，llama.cpp 自身对 cuBLAS 依赖轻（可选），但选框架时注意 vLLM 新版已不支持 P4——这是 llama.cpp 相对 vLLM 在老卡上的核心优势。

## 二、llama.cpp 系统功能

### 2.1 核心能力

| 能力 | 说明 |
|---|---|
| GGUF 推理 | 纯 C/C++ 核心（ggml/llama 库），无 Python/框架依赖；CPU-only 也能跑 |
| OpenAI 兼容 API | `llama-server`：`/v1/chat/completions`、`/v1/responses`、`/v1/completions`、`/v1/embeddings`、`/v1/models`，流式支持，客户端可直接复用 OpenAI SDK（改 base_url 即可） |
| 多用户并发 | `--parallel N` 并行槽 + continuous batching（持续批处理），支持 `--metrics` Prometheus 端点 |
| 多模态 | 通过 `--mmproj mmproj-*.gguf` 加载视觉投影器，图片输入（OpenAI 格式 image_url 或 base64） |
| 投机解码 | draft model 投机采样，server 端已内置，实测提速 25%~60%；Qwen3 等带 MTP 头的模型可直接受益 |
| Flash Attention | `--flash-attn on`（注意：仅 Turing+ 有 Tensor Core 才真正受益，Pascal 无 Tensor Core） |
| 量化生态 | Q2~Q8_K、IQ 系列、K-quants；自带量化/转换工具（full 镜像或 `convert_hf_to_gguf.py`）；imatrix 校准量化 |
| LoRA | `--lora` 运行时加载 LoRA 适配器，支持多 LoRA |
| 长上下文 | `-c` 任意指定（受显存/内存限制），支持 KV cache 量化（`--cache-type-k/v q8_0` 等）省显存 |
| 工具调用/JSON | grammar 约束生成（GBNF/JSON schema），`llama-server` 原生支持 tool calling |
| 多模型服务 | server 端 `--model` 多模型注册，同一端口切换 model 名 |
| 后端插件化 | 后端可编译为动态库运行时加载（`GGML_BACKEND_DL`），同一二进制跨机器换卡即用 |

### 2.2 GPU 后端矩阵

| 后端 | CMake 开关 | 适配硬件 |
|---|---|---|
| CUDA | `-DGGML_CUDA=ON` | NVIDIA（Turing 及以上官方预编译；Pascal/Maxwell 需自编译，见第五节） |
| ROCm/HIP | `-DGGML_HIP=ON` | AMD（gfx900+，消费卡需 HSA_OVERRIDE_GFX_VERSION） |
| Vulkan | `-DGGML_VULKAN=ON` | 几乎一切 GPU（含老卡、Intel 核显、移动 GPU）——**P4 的备选后端** |
| Metal | `-DGGML_METAL=ON` | Apple Silicon |
| SYCL | 见 docs/backend/SYCL.md | Intel CPU/核显/ARC GPU |
| MUSA | `-DGGML_MUSA=ON` | 摩尔线程 |
| OpenCL / CANN / ZenDNN / Hexagon 等 | 各自开关 | 对应平台 |
| 多后端共存 | 可同时开多个 | 运行时 `--device` 指定，`--list-devices` 查看 |

### 2.3 与 vLLM 的定位差异（内网选型视角）

| 维度 | llama.cpp | vLLM |
|---|---|---|
| 显存效率 | 极高（量化，8GB 卡能跑 8B 全量） | 低（主打 FP8/BF16 大显存） |
| 老卡（P4/T4/2080Ti） | **支持**（自编译 sm_61/75） | 新版已放弃 Pascal，T4 也边缘化 |
| 高吞吐 serving | 中等（continuous batching 有，但弱于 PagedAttention 优化深度） | 强（PagedAttention + 大 batch） |
| 多模态 | 有（mmproj，生态比 vLLM 少） | 强 |
| 投机解码/MTP | 内置，Qwen3 MTP 可用 | 支持 |
| 运维复杂度 | 单二进制/小镜像，极低 | 重（Python 依赖树大） |

## 三、部署方法

### 3.1 源码编译（P4 场景推荐路径，见第五节）

```bash
git clone https://github.com/ggml-org/llama.cpp && cd llama.cpp
# P4 (Pascal sm_61)：CUDA 必须 <=12.8，并显式指定架构
cmake -B build -DGGML_CUDA=ON -DCMAKE_CUDA_ARCHITECTURES=61 -DCMAKE_BUILD_TYPE=Release
cmake --build build --config Release -j
# 产物：build/bin/llama-server, build/bin/llama-cli 等
```

通用非 P4 机器（L20 sm_89 / 2080 Ti sm_75 双卡）：

```bash
cmake -B build -DGGML_CUDA=ON \
  -DCMAKE_CUDA_ARCHITECTURES="75;89" \
  -DCMAKE_BUILD_TYPE=Release
cmake --build build --config Release -j
```

### 3.2 Docker 部署

官方镜像（`ghcr.io/ggml-org/llama.cpp`）：

| 镜像 | 内容 | 平台 |
|---|---|---|
| `:server` / `:full` / `:light` | CPU 版（full 含转换+量化工具） | amd64/arm64/s390x |
| `:server-cuda` / `:full-cuda` | CUDA 版（**默认架构不含 Pascal**） | amd64 |
| `:server-vulkan` / `:server-rocm` / `:server-intel` / `:server-musa` | 对应后端 | amd64 |

- 直接跑（非 P4 卡）：

```bash
docker run --gpus all -v /path/to/models:/models -p 8080:8080 \
  ghcr.io/ggml-org/llama.cpp:server-cuda \
  -m /models/model.gguf --port 8080 --host 0.0.0.0 \
  -ngl 99 -c 8192
```

- **P4 必须自构建镜像**（官方镜像默认 CUDA 架构列表无 sm_61，2026-05 docker/model-runner 同款 issue 已实证该坑）：

```bash
cd llama.cpp
docker build -t local/llama.cpp:server-cuda-p4 --target server \
  --build-arg CUDA_VERSION=12.4.0 \
  --build-arg CUDA_DOCKER_ARCH=61 \
  -f .devops/cuda.Dockerfile .

docker run --gpus all -v /path/to/models:/models -p 8080:8080 \
  local/llama.cpp:server-cuda-p4 \
  -m /models/model.gguf --port 8080 --host 0.0.0.0 -ngl 99
```

- Docker Compose 最小形态：

```yaml
services:
  llama-server:
    image: local/llama.cpp:server-cuda-p4
    ports: ["8080:8080"]
    volumes: ["./models:/models"]
    environment:
      LLAMA_ARG_MODEL: /models/model.gguf
      LLAMA_ARG_CTX_SIZE: 8192
      LLAMA_ARG_N_PARALLEL: 2
      LLAMA_ARG_ENDPOINT_METRICS: 1
    deploy:
      resources:
        reservations:
          devices:
            - driver: nvidia
              count: 1
              capabilities: [gpu]
```

- Swarm/K8s：与现有平台一致——Swarm 用 `--gpus all` 服务约束 `com.docker.swarm.task.slot`；K8s 加 `nvidia.com/gpu: 1` 限额 + 卷挂模型目录。

### 3.3 Python 绑定（llama-cpp-python）

```bash
# CPU
pip install llama-cpp-python
# CUDA（P4 同理要指定架构）
CMAKE_ARGS="-DGGML_CUDA=on -DCMAKE_CUDA_ARCHITECTURES=61" \
  pip install llama-cpp-python --force-reinstall --no-cache-dir
```

```python
from llama_cpp import Llama
llm = Llama(model_path="./model-q4_k_m.gguf", n_ctx=4096, n_gpu_layers=99)
resp = llm.create_chat_completion(messages=[{"role": "user", "content": "你好"}])
```

嵌入式 server 也有：`pip install llama-cpp-python[server]` → `python -m llama_cpp.server --model ...`。

### 3.4 模型获取（HF Hub 直连）

```bash
# 直接从 Hub 拉取并运行（推荐写法）
llama-server -hf <repo>:Q4_K_M -c 8192 -ngl 99
# 精确文件
llama-server --hf-repo <repo> --hf-file <file.gguf>
```

注意：Ollama 的 GGUF 文件**不兼容**上游 llama.cpp（tensor 数量不匹配实测），必须从 HF 拿标准 GGUF。

## 四、P4 卡硬件画像与推理预期

| 项目 | 值 | 影响 |
|---|---|---|
| 架构 | Pascal GP102，sm_61 | CUDA ≤12.8 支持；CUDA 13.0 起编译支持移除 |
| 显存 | 8GB GDDR5（无 ECC 版本亦有） | 8B Q4_K_M（≈4.9GB）+ KV 可全量入卡 |
| 显存带宽 | 32 GB/s（GDDR5） | **性能瓶颈**：P40（345 GB/s）的 1/10 |
| Tensor Core | **无** | 启动日志会提示 `suboptimal performance due to a lack of tensor cores`；Flash Attention 无收益 |
| FP16 | 半速执行 | 推理主要用 Q8/Q5/Q4 定点核，影响有限 |
| 功耗 | 70W | 适合 7x24 常开小节点 |
| 驱动要求 | CUDA 12.x 需 ≥525 驱动；**必须专有内核模块**（开源内核模块仅支持 Turing+） | 老服务器装/升级驱动时注意 |

**性能预期（经验值，单卡 8B Q4_K_M 全量 offload）**：
- 生成（decode）：带宽受限 ≈ 32GB/s ÷ ~5GB 权重 ≈ 理论上限 6 t/s，实测一般 **4~8 t/s**；
- 预填充（prompt）：算力受限（~10 TFLOPS FP32 量级），几千 token prompt 约数秒；
- 对比：本机双 2080 Ti 跑 27B Q4_K_M + MTP 实测 52 t/s（2026-09 实测，见关联阅读）——P4 只能做 8B 以下的轻量活。

## 五、P4 支持：关键坑与标准解法

### 5.1 为什么"装好就跑"会翻车

预编译二进制/官方镜像的 CUDA 默认架构列表在 CUDA 12.x 后期已收窄（典型为 75/80/86/89/120/121，Turing 起），sm_61 不在内。P4 上启动症状（GitHub 多例实证）：

```
ggml_cuda_init: failed to initialize CUDA: forward compatibility was attempted on non supported HW
warning: no usable GPU found, --gpu-layers option will be ignored
```

**静默回退 CPU，GPU 利用率 0，没有任何报错**——这是最大的坑：不查 `nvidia-smi` 会以为正常在服务。

### 5.2 标准解法（三选一）

| 方案 | 做法 | 备注 |
|---|---|---|
| **A. 源码自编译（推荐）** | `cmake -B build -DGGML_CUDA=ON -DCMAKE_CUDA_ARCHITECTURES=61`，**CUDA toolkit 装 12.4~12.8**（勿装 13.x） | 一劳永逸，产物放服务器即可 |
| B. 自构建 Docker 镜像 | `--build-arg CUDA_VERSION=12.4.0 --build-arg CUDA_DOCKER_ARCH=61` | 见 3.2，适合平台化分发 |
| C. Vulkan 后端 | `-DGGML_VULKAN=ON`（或直接用 `:server-vulkan` 官方镜像） | 免 CUDA 版本问题；老卡通用；速度略低于调好的 CUDA，但 P4 这种带宽瓶颈卡差距不大 |

### 5.3 P4 部署验证 checklist

1. `nvidia-smi`：驱动 ≥525、专有内核模块（`cat /proc/driver/nvidia/version`）；
2. 构建日志确认 `GGML_CUDA: ON` 且架构含 `sm_61`（cmake configure 输出）；
3. 启动 `llama-server`，首行日志应出现 `CUDA0: NVIDIA T4/P4 (8192 MiB)` 而不是 `no usable GPU`；
4. `nvidia-smi` 观察显存被模型占用（8B Q4 ≈ 5-6GB）；
5. 请求一条对话，确认 t/s 落在 4~8 区间（8B Q4）而非 CPU 的 <2 t/s；
6. P4 无 Tensor Core，**不要开** `--flash-attn on`（无收益，白占调试时间）。

### 5.4 P4 能跑什么模型（8GB 预算）

| 模型规模 | 量化 | 占用 | offload 策略 | 预期 |
|---|---|---|---|---|
| 1.5B~4B | Q8/Q6 | 2~4GB | 全量 -ngl 99 | 流畅，10~25 t/s |
| 8B | Q4_K_M / Q5_K_M | 5~6.5GB（含 KV） | 全量 -ngl 99，KV 用 q8_0 | 4~8 t/s，可交互 |
| 8B 视觉（如 Qwen3-VL-8B） | Q4_K_M + mmproj | ~7GB | 全量（KV 压缩） | 可用，图片理解慢 |
| 14B | Q4_K_M | ~9GB | 混合：~一半层在卡 | 2~4 t/s，低并发可用 |
| 27B | Q4_K_M | ~17GB | 深度混合（大部分在 CPU 内存） | <2 t/s，仅批量非交互 |
| embedding 模型（0.6B~4B） | Q8 | 1~3GB | 全量 | 高吞吐，适合平台侧文本向量化 |

配套建议：`--cache-type-k q8_0 --cache-type-v q8_0` 把 KV 压一半；`--parallel 2` 开两个并发槽。

## 六、结合内网现状的落地建议

| 节点 | 卡 | 角色 | 方案 |
|---|---|---|---|
| 主力服务 | L20 48GB | 27B FP8 主力 API | vLLM + MTP（维持现有定案） |
| 辅助/边缘 | 2080 Ti ×2 | 中等模型、备份 | llama.cpp 自编译 `75`，Q4_K_M + MTP 投机（已实测 52 t/s） |
| 轻量辅助 | **P4** | embedding、意图分类、路由、小模型客服 | llama.cpp 自编译 `61`（或 Vulkan），8B 及以下 Q4；**不要**指望它跑 27B |

- P4 与 L20 之间可用同一套 OpenAI 兼容接口（llama-server / vLLM 都是），平台侧只配 base_url 即可分流：大任务 → L20/vLLM，小任务 → P4/llama.cpp；
- llama.cpp `--metrics` 端点接现有 Loki/Prometheus 监控即可；
- 镜像分发：把 `local/llama.cpp:server-cuda-p4` 推到内网 registry，Swarm service 声明 `nvidia.com/gpu: 1`。

## 七、风险与注意事项

1. **CUDA 13 断代**：新服务器若默认装 CUDA 13，P4 直接出局；P4 机器锁定 CUDA 12.4~12.8 + 专有驱动 525+（或走 Vulkan 后端彻底绕开）；
2. **静默 CPU 回退**：预编译产物上 Pascal 卡的默认行为，必须按 5.3 checklist 验证；
3. **P4 无 Tensor Core**：不要按"能跑"的口径承诺性能，decode 上限被 32GB/s 带宽锁死；
4. **生态收窄**：Pascal 的 CUDA 生态处于"feature-complete"状态（NVIDIA 官方口径），llama.cpp 自身不受影响，但其他库（cuDNN 等）新版不再支持，混用框架时要检查；
5. **Ollama GGUF 不兼容**：模型文件必须来自 HF 标准 GGUF（ggml-org / unsloth / bartowski 等）。
