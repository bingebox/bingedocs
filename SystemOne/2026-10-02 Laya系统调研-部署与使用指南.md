## 一、一分钟认识 Laya

Laya 是一个**非自回归 System 1 决策引擎**：不生成文本，单次前向传播对任意文本（100+ 语言）回答**类型化问题**，直接输出带校准概率的结构化决策：

| 基元 | 含义 | 例子 |
|---|---|---|
| `choice` | 从枚举选项中选一个 + 概率分布 | 工单归哪个队列（≤20 选项可靠） |
| `score` | 量表打分 + 概率分布 | 紧急程度 0–3 |
| `noul` | 真/假 0–1 概率 | 客户是否威胁解约 |

- **速度**：33ms/问、批量 7.2ms/问（T4 实测）；吞吐 103–332 问/秒；CPU 本机实测 ~0.8s/4 问（预热后）
- **训练**：RLCD（对严格恰当评分规则做强化学习），ECE 0.081（温度拟合后）
- **权重**：Apache-2.0，本地自托管 $0
- **三个检查点 + Router 按请求自动选**（脚本/语言检测，检测失败时 `LAYA_DEFAULT_MODEL` 兜底，0.3.23 起可配）：

| 检查点 | 编码器 | 参数 | 上下文 | 用途 |
|---|---|---|---|---|
| `laya`（english） | ModernBERT-large | 421M | 512 | 英文分类/守卫/分诊 |
| `laya-multilingual` | mmBERT-base | 322M | 1024（`max_len=8192` 可开长文） | **100+ 语言（含中文）**，快 2.2× |
| `laya-typed-decisions` | ModernBERT-large | 421M | 1024 | 微调版：agent 观测/客服/发票/安全告警（0.766 acc） |

**一句话定位**：把"高频、封闭答案、低复杂度"的判断（路由、分诊、守卫、门控）从 LLM 里剥出来，毫秒级、零成本、可分支（概率是校准过的，可以 `if p < 0.6: 升级 LLM`）。它**不写代码、不生成文本**，长文档深读仍是 LLM 的活。

## 二、怎么部署

Laya 不是"一个服务"，而是一组**可组合的部署形态**。按"从省到重"排序，生产上通常组合使用：一个推理后端（SDK/serve/Docker）+ 若干接入面（MCP/HTTP/进程内）。

### 2.1 形态总览（选型先读这张表）

| 形态 | 部署命令 | 适合 | 需要代码 |
|---|---|---|---|
| **本地 venv（pip）** | `pip install "laya[mcp,serve]"` | PoC、单机、agent 集成 | 否 |
| **Docker（官方 compose）** | `docker compose run --build --rm laya` | 内网/生产、环境隔离、**国内 ModelScope 烘焙** | 否 |
| **laya-serve 裸机 HTTP** | `laya-serve` | 已有 Jev 客户端改 baseUrl、CI/后端直调 | 否 |
| **MCP server（stdio）** | `laya-mcp-server` | 一切 MCP 客户端（Claude Code/Hermes/Cursor/DSH…） | 否（一条配置） |
| **托管 MCP（laya.studio）** | 粘贴 `https://api.laya.studio/mcp` + Bearer key | 零运维、不想本地装 | 否（付费，数据出境） |
| **进程内 SDK** | `from laya import Router` | 热路径低延迟、批量管线、深度门控 | 少量（调用+门控） |

### 2.2 形态一：本地 venv（最快上手）

**前置**：Python ≥ 3.10（依赖 huggingface_hub 1.x / transformers 5.x / torch 2.14 共同抬高下限）。

```bash
# macOS / Linux
python3 -m venv ~/.venvs/laya
~/.venvs/laya/bin/python -m pip install "laya[mcp,serve]"
# CPU 机器建议先装 CPU 版 torch，避免误装多 GB CUDA 包：
# ~/.venvs/laya/bin/python -m pip install torch --index-url https://download.pytorch.org/whl/cpu

# Windows PowerShell（本机环境）
py -3.11 -m venv D:\.venvs\laya
D:\.venvs\laya\Scripts\python.exe -m pip install "laya[mcp,serve]"

# uv 用户
uv venv --python 3.12 && uv pip install laya   # --torch-backend=cpu 可自动选 torch 构建

# 验证（不加载检查点，纯检查安装）
~/.venvs/laya/bin/python -I -c "import laya; print(laya.__version__)"
```

可选 extras：`laya[serve]`（HTTP）、`laya[mcp]`（MCP）、`laya[langchain]`、`laya[llamaindex]`、`laya[crewai]`、`laya[onnx]`（ONNX Runtime）、`laya[fast]`（TileLang GPU 快速路径）。
Intel GPU（XPU）：先装 `torch --index-url https://download.pytorch.org/whl/xpu` 再装 laya，`device="xpu"` 显式指定。

**检查点下载**：`Router()` 是惰性的——首次 predict 只下载被路由选中的那个检查点，之后复用 HF 缓存（`HF_HUB_CACHE` 可改位置）。english/typed-decisions 各 ~421M 参数，multilingual ~322M。

**国内网络踩坑（本机实测，0.3.22）**：
```bash
export HF_ENDPOINT=https://hf-mirror.com
export HF_HUB_DISABLE_XET=1      # 关键！否则 hf_xet 走 cas-server.xethub.hf.co 401
                                 # HF_HUB_DOWNLOAD_XET 是错的，正解是 DISABLE
# 检查点缓存就位后，服务端加 HF_HUB_OFFLINE=1 最干净（免每次 revision 检查）
```

**内存管理**：`Router()` 默认常驻最多 2 个检查点（`max_loaded=2`，LRU 驱逐）；`Router(preload=True)` 一次载入全部三个（会抬高常驻上限，**不是** OOM 补救）；`Router(max_loaded=1)` 降内存但切换检查点要重载（7–10s/次）。

### 2.3 形态二：Docker（官方 compose，生产推荐）

仓库自带 `compose.yaml`（CPU）+ `compose.cuda.yaml`（GPU）+ `compose.http.yaml`（HTTP 服务）+ `compose.example.yml`（注释版示例）+ `compose.modelscope.yaml`（国内源）。

**CPU 快速开始**（8 GB RAM / 10 GB 磁盘，首次下载检查点需几分钟）：

```bash
git clone https://github.com/NandhaKishorM/laya && cd laya
docker compose run --build --rm laya          # 跑官方示例请求，输出三基元 JSON
docker compose run --rm laya                  # 之后：权重留在命名卷里，秒起
```

**GPU**（NVIDIA Container Toolkit + CUDA 12.8 wheels；镜像内置 `TORCH_DISABLE_NATIVE_JIT=1`，否则 slim 镜像缺 C 编译器，健康检查过后每个请求都 500）：

```bash
docker compose -f compose.yaml -f compose.cuda.yaml run --build --rm laya
# LAYA_GPU_ID 换卡；CPU↔GPU 切换要重新 build
```

**HTTP 常驻服务**（同一镜像自带 `laya-serve`）：

```bash
docker compose -f compose.yaml -f compose.http.yaml up -d --wait laya-serve
curl -s localhost:8000/health
curl -s localhost:8000/v1/systemone -H 'content-type: application/json' --data @examples/docker/request.json
```

**国内内网关键能力：ModelScope 烘焙（0.3.23 前后上线，PR #720）**

宿主机连不上 huggingface.co 时，构建期从 modelscope.cn 把检查点烤进镜像，容器运行时**完全离线**：

```bash
docker compose -f compose.yaml -f compose.http.yaml -f compose.modelscope.yaml up --build laya-serve
# 或 plain docker：
docker build --build-arg MODELSCOPE_MODEL=multilingual -t laya:local .
docker run --rm -e HF_HUB_OFFLINE=1 -p 127.0.0.1:8000:8000 laya:local laya-serve
```

- `MODELSCOPE_MODEL`：`multilingual`（默认）/ `english` / `typed-decisions` / `all`（全家桶 ≈2.4 GB；双检查点 `"english multilingual"` ≈1.5 GB，Router 自动二选一；**少烤一个，路由命中它会 500** `does not contain 'rl_agent_config.json'`）；也支持 `repo[:subfolder]` 烤独立镜像仓库或**自己的微调检查点**
- compose 覆盖层自动设 `HF_HUB_OFFLINE=1` 和 `LAYA_MODELS=multilingual`（烤了多个就改）
- **卷残留坑（官方明示）**：命名卷只在为空时从镜像播种。如果之前跑过 Hub 版 quickstart，旧卷会挡住烘焙的权重（loader 解析到旧 Hub commit，"像什么都没变"）。换新部署要 `docker compose down --volumes`（同 compose 文件、同 `LAYA_CACHE_VOLUME`）或换新卷名
- 供应链：权重来自 modelscope.cn 上对应账号的镜像，构建期做 size（有 digest 做 SHA-256）校验——镜像账号是部署方自己的选型决策

**其他 Docker 要点**：

| 变量 | 默认 | 用途 |
|---|---|---|
| `LAYA_DEVICE` | cpu / cuda | 设备 |
| `LAYA_MODEL` | auto | Router 别名 auto/english/multilingual/typed-decisions |
| `LAYA_MODEL_PATH` | — | 容器内自定义检查点目录（微调模型） |
| `LAYA_REVISION` | — | Hub commit/branch/tag 钉住下载；`reviewed` = 审查过的 SHA 集 |
| `LAYA_REQUEST_FILE` | 内置示例 | 一次式请求 JSON 路径 |
| `OMP_NUM_THREADS` | 4 | CPU 线程，别超物理核 |
| `HF_TOKEN` / `HF_TOKEN_FILE` | — | HF 凭据（文件优先，挂载给 UID 10001 可读） |
| `LAYA_API_KEY` / `LAYA_API_KEY_FILE` | — | **仅 laya-serve**：Bearer 认证 |
| `LAYA_PORT` | 8000 | 容器端口 + 宿主机发布端口（一处改两处动） |
| `HF_HUB_OFFLINE` | 0 | 1 = 只用缓存 |
| `LAYA_CACHE_VOLUME` | 项目 model-cache | Compose 专用：权重卷名 |
| `LAYA_GPU_ID` / `LAYA_TORCH_INDEX` / `LAYA_TORCH_VERSION` | 0 / cu128 / 2.14.0 | Compose 专用：GPU 与构建参数 |

- 镜像以 **UID/GID 10001** 运行：挂载的宿主机目录（含自定义检查点目录，loader 可能要更新 tokenizer 配置）必须可写；**LoRA adapter 单独不算完整检查点**
- 自定义微调检查点：`LAYA_MODEL_PATH=/models/custom` 指向含 `rl_agent_config.json` + `model.safetensors` + tokenizer 的目录；此时 `LAYA_MODEL` 保持 auto（别名与本地路径互斥）；响应来自 Agent，**没有 Router 的 `routing` 元数据**
- 删除已下载权重：`docker compose down --volumes`（用同一组 compose 文件）
- ARM64/DGX Spark/Apple Silicon 有单独的容器文档（`docs/docker-platforms.md`）；MPS/ROCm/Intel GPU 容器不在 quickstart 范围

### 2.4 形态三：laya-serve 裸机 HTTP（Jev 兼容 API）

```bash
pip install "laya[serve]"
LAYA_DEVICE=cuda LAYA_PRELOAD=1 laya-serve     # 默认绑 0.0.0.0:8000，预载全部检查点
```

端点：

- `POST /v1/systemone` —— 与 TypeSafe Jev **同一 wire protocol**：现有 Jev 客户端（如 hs-jev Haskell client）改 `baseUrl` 即可，payload schema 完全相同（choice/score/noul 答案 + `{input_tokens, output_tokens}` usage 块）
- `POST /v1/systemone/batch` —— `states` 数组，**上限 64**，共享前向，按输入顺序返回 + 聚合 `total_usage`（0.3.23 起同样转发 `lang/lang_guess/min_confidence/task/max_len/head_max_len`）
- `GET /health` —— 存活检查；报告**检查点实际运行的设备**（GPU 丢了会静默回退 CPU，`checkpoint_devices`/`device_is_preference` 字段说清楚）+ CPU 回退计数；**0.3.23 起**：设置了 `LAYA_API_KEY` 时，未认证调用只回 `{"status":"ok"}`，检查点名/revision SHA/设备态需要 Bearer

请求体除了 `state`/`questions` 还可带 `model`（点名检查点，否则 Router 自动选）、`task`、`lang`、`lang_guess`、`min_confidence`、`max_len`、`head_max_len`；五个 hook 参数是 callable，HTTP 上给会被 **422** 拒绝。

**完整环境变量**（serve 契约，MCP 也复用同一套语义）：

| 变量 | 默认 | 说明 |
|---|---|---|
| `LAYA_HOST` / `LAYA_PORT` | 0.0.0.0 / 8000 | 绑定地址与端口 |
| `LAYA_DEVICE` | auto | `cuda`/`cuda:0`/`cpu`（小写，torch 解析大小写敏感） |
| `LAYA_PRELOAD` | serve 默认 1 / Docker 里 0 | 1 = 启动时建好全部检查点（常驻部署设 1，首请求免建） |
| `LAYA_MODELS` | 全部 | 逗号列表限定预载：`english,multilingual` |
| `LAYA_THREADS` | torch 默认 | CPU intra-op 线程上限，≤物理核 |
| `LAYA_AUTO_TASK` | 0 | 1 = question id 匹配 typed-decisions 工作流的请求自动路由过去（按需加载，不进预载列表） |
| `LAYA_DEFAULT_MODEL` | english | **0.3.23**：无语言证据的 state 的兜底检查点；中文为主流量设 `multilingual`；填错容器启动即失败 |
| `LAYA_MAX_LOADED` | 2 | 常驻检查点数；开了 AUTO_TASK 要提到 3，否则每次路由切换都重建 |
| `LAYA_MAX_CONCURRENT` | 16 | 并发上限，超了 503（带 `Retry-After`） |
| `LAYA_LOG_LEVEL` | info | uvicorn 日志级 |
| `LAYA_API_KEY` | — | 设置后要求 `Authorization: Bearer <key>` |
| `LAYA_ROOT_PATH` | 空 | 反代前缀（代理要剥离前缀再转发） |
| `LAYA_MAX_TOKEN_BUDGET` | 8192 | 每请求 `max_len`/`head_max_len` 覆盖值的上限 |
| `LAYA_SHA256_DIGESTS` | — | 检查点解析前校验 `{artifact: digest}`（安全） |
| `LAYA_CUDA_AMP` / `LAYA_CPU_AMP` | 检查点 amp_dtype | fp16/bf16；**bf16 比 fp16 会翻转更多 argmax**（60 状态 288 问：bf16 翻 3/864，fp16 翻 0）——阈值要在你服务的 dtype 上拟合 |

**与 Jev 的三个差异（迁移客户端必读）**：

1. **选项数**：选项共享 `head_max_len` 预算（english 192 / 其他 256 token），不是 Jev 的 255 选项；serve 还有 `MAX_CHOICE_OPTIONS=100` 防放大上限（超了 413）；塞满后每个选项被截到同长度，~20 个短描述选项以上就开始掉——更多候选先 `predict_shortlist`
2. **score 每级必须有描述**，null 级直接 422
3. **confidence 定义不同**：Laya 的 choice/score `confidence` = 1 − 归一化熵（分布集中度），不是 Jev 的 `(n·p_max−1)/(n−1)`——**Jev 上的阈值不能照搬**；要单一校准数，门控用 **`answer_confidence`**（报告答案的概率本身）

**生产建议**：默认只发布到 `127.0.0.1`；要对外先设 `LAYA_API_KEY`（优先 `LAYA_API_KEY_FILE` 文件挂载），`LAYA_BIND_ADDRESS=0.0.0.0` + TLS 反代；反代下加 `LAYA_ROOT_PATH`；`up -d --wait` 配合 `/health` healthcheck 保证"健康 = 检查点已加载"。

### 2.5 形态四：MCP server（agent 集成首选）

```bash
pip install "laya[mcp]"
laya-mcp-server          # 或 python -m laya.mcp.server
```

stdio 传输，**8 个工具**：`laya_predict` / `laya_predict_batch` / `laya_route` / `laya_route_batch` / `laya_decide` / `laya_shortlist` / `laya_preset` / `laya_status`。返回结构化 JSON（概率分布、路由元数据、设备、`latency_ms`）。

任意 MCP 客户端的配置（Claude Code / Hermes / omp / Cursor / DSH / QwenPaw / WorkBuddy 同一套）：

```json
{
  "mcpServers": {
    "laya": {
      "command": "laya-mcp-server",
      "env": { "LAYA_DEVICE": "cpu", "LAYA_MODELS": "multilingual" }
    }
  }
}
```

环境变量与 serve 同契约，MCP 差异两处：`LAYA_PRELOAD` 默认 **1**；`LAYA_MODELS` 默认 `english,multilingual`（空值也是这两个，typed-decisions 保持惰性——serve 里空值 = 全部）。

**batch 工具值得优先用**：`laya_predict_batch` 一次传数组，先路由、按检查点分组、同 schema 共享前向，按输入顺序返回（每项可带自己的 `max_len/head_max_len`）。实测 16 条混合语言工单：MPS 上比 16 次单调用快 **2.1–2.3×**，CPU 上 ~1.25×，**0/16 决策翻转**。0.3.23 起该工具转发 `hooks_timeout`/`min_confidence`/`sort_by_length`。

**本地 MCP 接入的两个坑（本机实测 0.3.22，写自研 client 前必读）**：

1. 官方 `laya-mcp-server` 在 `server.run()` 前**同步预加载**检查点（CPU 6–10s），事件循环不转 → mcp 2.2 SDK 客户端 `initialize` 握手 10s 超时。解法：包装器把预加载放后台守护线程（本机 `laya-mcp-async`，见 2026-10-01 文档 7.4 节），握手 0.8s 返回
2. mcp 2.2 SDK `tools/call` **默认请求超时 10s**，CPU 推理 8–30s → 自研 client 必须调大；GPU 33ms 无所谓

### 2.6 形态五：托管 MCP（laya.studio，免运维）

`https://api.laya.studio/mcp`（Streamable HTTP，Bearer key），6 个工具（`decide`/`classify`/`yes_no`/`score` 等），任何 MCP 客户端粘贴 URL + header 即用。按输入 token 计费（1 credit = 1 input token）——**数据出境 + 高频批量成本**，内网平台场景建议全本地。

### 2.7 其他部署形态

- **Nix/NixOS**：仓库是 flake，GPU 机器 `nix run` 直接跑（`docs` 有命令）
- **ONNX**：`scripts/export_onnx.py`（0.3.23 起 `--quantize` 默认 per-tensor——per-channel 会把模型搞崩到 32% 一致率；torch<2.9 的动态维声明已修）；`ONNXAgent` 支持 `predict_batch`/`predict_long`/`decide_batch`；`laya-evals run --onnx --calibration` 可对导出件评分
- **TypeScript**：`laya-ts`（npm，从 `laya-ts-v*` tag 发版）——Node/浏览器 ONNX，可直连自托管 `/v1/systemone`
- **社区移植**：`laya-Ascend`（华为 NPU，bs=1 比 CPU 快 34–71×）、`laya-apple`（MLX + ANE，异构并发）、`laya-mlx`（13.4ms/短决策）、`stuntd`（Jev 兼容本地端点 + 按决策项训 head，12 标签意图 89.5%→100%）、`omp-laya-judge`（omp 插件：本地 System-1 裁判 MCP + skill，CPU ~0.3s）、`laya-adk-toolkit`（Google ADK）
- **GPU 快速路径**：`laya[fast]`（TileLang）+ `compile=True` + `agent.warmup()`（服务前预热；0.3.21 起 compile 不再每 shape 重编；0.3.23 跨 token 长度复用 CUDA graph）

### 2.8 部署选型速查

| 场景 | 推荐部署 | 关键配置 |
|---|---|---|
| 本机 PoC（验证中文效果/延迟） | venv + CPU | `laya[mcp,serve]`，`HF_ENDPOINT` 镜像 + `HF_HUB_DISABLE_XET=1` |
| Agent 集成（Claude Code/Hermes/omp…） | 本地 `laya-mcp-server`（stdio） | `LAYA_MODELS=multilingual`；注意 2.5 节两个超时坑 |

## 三、怎么使用

### 3.1 Python SDK（核心用法）

```python
from laya import Router

router = Router(preload=True)   # 三个检查点常驻，免切换冷启动 7–10s
# Router() 惰性：首次 predict 才下载被路由命中的检查点

state = "【P1告警】prod-face-recognition P95 延迟 120ms→4.2s，错误率 38%，2000 员工无法打卡"
questions = {
    "queue": {"type": "choice", "instructions": "归哪个工程队列？",
              "criteria": {"infra": "宕机/网络/数据库", "ml_platform": "模型/特征/推理链路",
                           "network": "网络/CDN", "billing": "退款/发票"}},
    "urgency": {"type": "score", "instructions": "多紧急？",
                "criteria": ["不紧急", "尽快", "高优先级", "critical 阻塞"]},
    "is_model_related": {"type": "noul", "instructions": "是否与模型/推理链路相关？"},
}

res = router.predict(state, questions)        # 一次前向，三个问题全答
print(res["routing"]["model"])                # multilingual（脚本检测：han）
print(res["answers"]["queue"]["choice"])      # ml_platform
print(res["answers"]["queue"]["answer_confidence"])  # 门控用这个，不是 confidence
print(res["answers"]["is_model_related"]["noul"])    # 0.9995，可直接 if 分支
```

关键调用形态：

| 调用 | 用途 |
|---|---|
| `router.predict(state, questions, model=..., lang=..., lang_guess=..., max_len=..., head_max_len=..., min_confidence=...)` | 单请求；`model` 点名检查点；`lang` 强制、`lang_guess` 软提示（0.3.23 全 surface 贯通） |
| `router.predict_batch(states, questions, sort_by_length=True)` | 批量共享前向；按长度分组实测 1.42×（128 条 Yelp 配对中位）/ 2.15×（1 万合成）；结果保持输入顺序 |
| `router.predict_long(...)` | 长文档滑动窗口（0.3.23 修复了窗口裁剪问题）；`laya-multilingual` 配 `max_len=8192`：前 ~4000 token 内 16–18/20 正确，再往后 8–17/20 波动，**长文精度必须自测** |
| `router.decide(state, schema)` / `decide_batch` | **schema 驱动**：给 JSON schema（enum/bool/有界整数），直接返回投到 schema 上的值 + 逐字段 confidence/probabilities——已知答案形状时不用手工解析 answer map |
| `laya.predict_shortlist(agent, state, questions, embed_fn=laya.embed_fn_from_agent(agent), k=20)` | >20 选项的 choice：先用编码器自身 embedding 余弦相似度截 top-k，再一次前向答；配 `laya.cached_embed_fn` 缓存不变的选项向量（LRU 4096） |
| `router.route(state)` | 只路由不推理，毫秒级、**不下载检查点**——适合前置门控"这条该进 System 1 吗" |

### 3.2 问题（questions）怎么写——决定效果的核心

```json
{
  "问题名": {
    "type": "choice | score | noul",
    "instructions": "一句话问什么",
    "criteria": {"选项key": "选项描述", ...}   // choice/score
                // noul: {"true": "...", "false": "..."} 或省略（通用对）
  }
}
```

**必须遵守的设计规则（官方 honest limits，踩坑成本很高）**：

1. **choice 选项 ≤20**（共享 192/256 token 的 head 预算；77 选项时每标签只剩 3–4 token，Banking77 掉到 0.425 vs Jev 0.870）。更多选项：`predict_shortlist` 两级化，或拆 coarse→fine 两问
2. **choice 的 key 别用 `true`/`false`/`yes`/`no`**：key 是原样渲染给模型的文本，检查点可能跟着标签走而不看 state。用语义标签或不透明标签（`A`/`B`）并在自己的数据上验证
3. **语义标签 ≠ 否定安全**：`no_action`/`cancel_account` 这类 key 在否定句（"我不打算取消"）上 4/4 选错 `cancel_account`（multilingual 2/4，其中一条概率 0.9998）——**要服务的检查点+措辞必须验证否定句**
4. **noul 在 english 检查点上可能跟 `true:`/`false:` 标签走**（#156：明显肯定输入自信答 "no"）；无 criteria 的 noul 在 english 上对所有 state 答 "no"。对策：criteria 写满（key 必须是 true/false），或用 `labels: {"true": "A", "false": "B"}` 改模型看到的措辞（结果仍按 P(true) 报）；multilingual 上无 criteria 形式能读 state
5. **multilingual 的 score 有位置偏差**（#131：很少选第一个列表项）——英文 score 问题路由到 `model="english"`，其他语言自测后再信
6. **score 每级都要描述**；**head 预算**：`head_max_len` 是上限不是实际长度，state 实际可用空间 = `max_len − 实际 head 长度 − 1`（选项多时 head 会**超过**上限，按上限估 state 会被截断）
7. 批量问题（k 个旋转）可以合并成 k 个问题共享一次前向

### 3.3 置信度与门控（System One 的核心价值）

- **门控用 `answer_confidence`**（报告答案的概率，校准过的），**不是** `confidence`（=1−熵，集中度，选项数敏感，Jev 阈值不可迁移）
- **弃权机制**：`predict(..., min_confidence=0.6)` → 低于阈值的答案标 `low_confidence: True`；`decide()` 直接返回 `None`（"不确定就不许动作"）。0.3.23 起每个答案还报 `abstention`（`passed`/`abstained`/`unevaluated`）——能区分"门控放行了"和"门控没跑"
- **典型门控**：`p < 0.6` → 升级 LLM（System 2）复核。本机实测（2026-10-01，中文 P1 告警，零样本）：noul 两问 0.99+ 直接可用；score 紧急度 P1=0.72 可分支；choice 队列归属置信度 0.21（三选各 0.28–0.35）→ 按设计升级 LLM。**门控按设计工作了**：模型诚实地不确定，而不是自信地答错
- 阈值要在**你的服务 dtype**（fp16/bf16/fp32）和选项数上重新拟合——bf16 会翻转更多 argmax

### 3.4 CLI（免写脚本）

```bash
laya "I was charged twice, please refund"              # 只路由，毫秒级，离线不下载
laya "Refactor this service" --predict                 # 完整答案（首次下载检查点）
laya "Mein Konto wurde zweimal belastet" --lang de     # 强制语言
laya "My payment failed twice" --lang-guess en         # 软提示（0.3.23）
laya "..." --model ml                                  # 点名检查点
laya "My payment failed twice" --preset triage         # 内置 preset：triage/email/guard/moderation/router
laya --batch tickets.txt --predict                     # 整文件一批（同进程共享加载与前向）
cat tickets.txt | laya --batch - --predict --json      # stdin，JSONL 输出
laya --batch f --predict --batch-size 8 --sort-by-length  # 按长度分组（1.42×，需 1<N<条数）
laya "Where is my card" --questions intents.json       # 自定义问题（JSON 文件）
laya "Refund my card" --predict --min-confidence 0.9   # 标记低置信（0.3.23）
laya                                                   # 交互模式
```

### 3.7 MCP 客户端（agent 用）

工具选择：**`laya_predict`**（返回完整分布，让 LLM 自己看）vs **`laya_decide`**（带 `min_confidence`，低置信直接 null，"不确定就不许动作"）vs **`laya_predict_batch`**（多条优先）vs **`laya_shortlist`**（>20 选项）vs **`laya_preset`**（triage 等现成套件）vs **`laya_status`**（自检：检查点/设备/版本）。

### 3.8 框架集成

- **LangChain/LangGraph**（`laya[langchain]`）：`LayaDecision` 节点——sub-35ms 条件边路由 + 置信回退、内联 prompt 守卫、schema 驱动决策、`batch()`/`abatch()` 批量
- **LlamaIndex**（`laya[llamaindex]`）：selector 组件
- **CrewAI**（`laya[crewai]`）：routing
- 三个 wrapper 在 0.3.23 统一把 `confidence_threshold` 门控在 `answer_confidence` 上（之前误用熵置信度）

### 3.9 评测与持续质量（laya-evals）

```bash
laya-evals validate data.jsonl
laya-evals run data.jsonl --model english --min-accuracy 0.8 --max-ece 0.05 --slice language
laya-evals run data.jsonl --baseline baseline.json --tolerance choice_accuracy=0.02 --json report.json
```

纯 Python+numpy、不 import torch、不加载权重也能跑；报总体 + 分片指标（`choice_accuracy`/`noul_accuracy`/`score_mae`/`ece`/`mean_confidence`/latency），超阈值/基线失败**非零退出**——直接挂 CI。0.3.23 新增：分片质量门（整体涨但分片跌能抓到）、shortlist 错误归因（检索 vs 决策）、`--min-confidence` 进弃权门、ONNX 路径 `--calibration`。

**接入生产前的最低验证动作**：用自己域的 50–100 条真实状态（告警/工单/消息）构造标注集 → `laya-evals run` → 记录 accuracy 与 ECE → 决定是否微调。**零样本精度不满足就微调，别硬用。**

### 3.10 微调（精度的真正来源）

**基座检查点在 typed-decisions 上零样本近随机**（0.362/0.352 vs 随机 0.318 / 多数类 0.461）；微调版 0.766（> Jev 0.727，> 教师自一致上限 0.735）。**Laya 是"快速可特化的基座"，不是"零样本决策引擎"。**

- **Kaggle 2×T4 notebook**（免费 4 小时档，DDP）：全流程——建数据集 → RLCD 训练（恰当评分规则奖励，GRPO 式策略梯度）→ 温度校准 → 评测 → 推 Hub；~4–5 小时/4 epochs/~30k 问题
- **Apple Silicon MPS 脚本**（16 GB 笔记本可跑）：`python notebooks/laya_finetune_typed_decisions_mps.py --micro-batch 1 --grad-accum 32`
- 校准注意：notebook 按类型（choice/score/noul）拟合温度并**删除**继承的 `temperature_by_options`（否则旧桶值在推理时压过新拟合，静默失真）；校准样本来自训练项，**声明改进前要在独立 held-out 数据上评**
- 参考实战：browser-agent 决策头（单张 16 GB GPU 免费 API）——元素 top-1 从 0.10 → 0.66，真实任务成功率 0% → 62%，17–23ms/步，权重在 HF `cklxx/laya-browser`
- 微调产物部署：`LAYA_MODEL_PATH` 挂载（Docker）或本地路径直载

| 变化 | 影响 |
|---|---|

## 五、已知边界（写进任何方案都要带）

1. **零样本近随机**（typed-decisions 0.362）→ 生产关键判断必须微调或门控兜底
2. **choice >20 选项掉点**（Banking77 0.425 vs Jev 0.870）→ ≤20 或 shortlist 两级化
3. **上下文短**：512/1024 token（multilingual 可 8192，>4k 精度波动）——长状态是 Jev（32k）的绝对优势区
4. **base 过度自信**：原始 ECE 0.466/0.314，温度拟合后 0.081/0.106；multilingual 出厂**不带**拟合温度，用它的概率前先拟合
5. **noul/score 的标签敏感性与位置偏差**（3.2 节规则 4/5）
6. **`action.act_probability` 无信号**（AUROC 0.30）——门控用 `confidence`（AUROC 0.77）
7. **项目年轻**：2026-09-18 首发，两周内 29.5k★、25+ release，接口可能变——**生产 pin 版本**（当前 0.3.23）
8. **自述基准**：vs Jev 的对比数字是作者自测（Jev 侧来自第三方 236–276ms p50），正式决策用自己的 `laya-evals` 数据
